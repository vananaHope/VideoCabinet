# 구현 작업 명세 양식

`<...>`를 채워 Codex 작업자에게 보낸다. 이슈별로 바뀌는 곳은 Change와 범위 밖 목록뿐이다.

```markdown
# 작업: GitHub 이슈 #<n> "<이슈 제목>" 구현

당신은 이 작업의 구현 담당입니다. 끝나면 관리자(Claude)가 별도 에이전트로 교차 검토합니다.

## 먼저 읽을 것 (필수)

- `gh issue view <n> --comments` : 완료 기준 체크리스트와, 앞선 이슈에서 넘어온 지적(댓글). 이것이 기준이다.
- `gh issue view 1` : 전체 스펙. 특히 "Implementation Decisions", "Testing Decisions".
- `AGENTS.md`, `CONTEXT.md`(용어집), `docs/adr/`, `README.md`(환경 준비·실행)

## Target

현재 worktree(`main`에서 분기한 이 작업 전용 브랜치). <이 이슈가 주로 건드릴 영역: 앱 코어의 어느 부분, 화면, 어댑터 등>

## Change

이슈 #<n>의 완료 기준을 모두 만족시킨다. <기준을 짧게 요약하고, 이슈 댓글로 넘어온 지적이 있으면 함께 처리하라고 적는다.>

## Constraints

- 기술 스택은 ADR-0001 그대로(Python + PySide6 + mpv). 도메인 규칙은 앱 코어에, 외부 세계(미디어 정보, 받아쓰기, 번역, 시계)는 주입 가능한 어댑터로 둔다.
- 코드의 도메인 이름은 `CONTEXT.md` 용어의 영어 표기를 쓴다. 용어집에 없는 도메인 개념을 새로 만들어야 하면 완료 보고에 적는다.
- 테스트는 앱 코어의 공개 동작(또는 떼어낸 순수 함수)만 검증한다. 내부 테이블이나 private 함수에 묶지 않는다.
- 범위 밖(다른 이슈가 맡음, 만들지 않는다): <이슈 번호와 기능 목록>. 그것들이 들어올 자리를 막는 구조로도 만들지 않는다.
- 커밋 메시지는 한국어. 의미 단위로 여러 번 커밋해도 된다. push, PR 생성, `main` 병합은 하지 않는다.
- 이 worktree 밖의 파일은 건드리지 않는다. 시스템 수준 설치나 업그레이드가 필요하면 해도 되지만, 무엇을 했는지 완료 보고에 적는다. 검증 기록은 저장소에 커밋하지 말고 완료 보고에 담는다.

## Ownership

이 worktree 안의 파일만 편집한다. <다른 작업자가 동시에 진행 중인 이슈가 있으면: "#<m>이 동시에 진행 중이며 <영역>을 건드린다. 공용 부분(DB 스키마 등)을 바꿀 때는 그 사실을 완료 보고에 적는다.">

## 테스트 실행

- 작업하는 동안에는 바꾼 모듈과 관련된 테스트만 돌린다. 예: `pytest tests/test_<영역>*.py -q`
- 전체 `pytest`는 **제출 직전에 한 번** 돌린다. `pytest-xdist`가 설치돼 있으면 `pytest -n auto`로 돌린다.
- 다른 작업자도 같은 PC에서 테스트를 돌린다. 전체 실행을 여러 번 반복하지 않는다.

## 제출 전 자기 점검

`<메인 저장소>/.claude/skills/orchestrate-issues/common-findings.md`(자주 나온 검토 지적 10유형)를 읽는다. 이번 변경에 해당하는 유형마다 그 "점검"을 실제로 해 본다. 완료 보고에 유형별로 "해당 없음 / 확인함(방법) / 남김(이유)"을 한 줄씩 적는다.

## Observable acceptance

- `gh issue view <n>`의 완료 기준이 모두 충족된다.
- 환경은 `scripts/setup.ps1 -Worktree`로 준비한다(빠른 모드).
- README 절차로 준비한 환경에서 `pytest` 전체가 통과한다(제출 직전 1회).
- 자기 점검 결과가 완료 보고에 있다.
- `worker_done` 요약에 다음을 담는다: 커밋 해시, 테스트 결과(통과 수), 설치하거나 바꾼 시스템 구성 요소, 사람이 직접 확인해야 할 항목, 충족하지 못했거나 판단이 필요했던 항목.
- 막히거나 스펙이 모호하면 추측하지 말고 orchestration `ask`로 관리자에게 질문한다.
```
