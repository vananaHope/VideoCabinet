# 교차 검토 명세 양식

`<...>`를 채워 Claude 검토자에게 보낸다. 보고서 경로는 `.local/orchestration/issue-<n>/`의 절대 경로로 쓴다(검토자는 worktree에서 실행된다).

```markdown
# 작업: GitHub 이슈 #<n> 구현의 교차 검토 (검토 전용, 파일 수정 금지)

당신은 교차 검토자입니다. 다른 에이전트(Codex)가 이 worktree에서 이슈 #<n>을 구현했습니다. 구현 과정의 맥락 없이 결과물만 보고 독립적으로 판단하세요.

## 먼저 읽을 것

- `gh issue view <n> --comments` : 완료 기준 체크리스트(판정 기준)와 앞선 이슈에서 넘어온 지적
- `gh issue view 1` : 전체 스펙, 특히 "Implementation Decisions", "Testing Decisions", "Out of Scope"
- `AGENTS.md`, `CONTEXT.md`, `docs/adr/`
- 변경 내용: `git log --oneline main..HEAD`, `git diff main...HEAD`

## 검토 항목

1. **완료 기준**: 항목마다 충족 / 미충족 / 자동 확인 불가(사람이 봐야 함)를 판정하고 근거(파일·테스트 이름)를 단다.
2. **테스트 실제 실행**: 변경과 관련된 테스트만 `pytest -n auto`로 한 번 돌려 결과를 기록한다. 전체 `pytest`는 돌리지 않는다(관리자가 Release 직전 `main`에서 돌린다).
2-1. **자주 나온 지적**: `<메인 저장소>/.claude/skills/orchestrate-issues/common-findings.md`의 10유형을 먼저 확인한다. 구현자의 완료 보고에 있는 자기 점검 결과가 맞는지도 확인한다.
3. **아키텍처**: 도메인 규칙이 화면이 아니라 앱 코어에 있는가. 외부 세계가 주입 가능한 어댑터인가. ADR과 어긋나는 곳이 있는가.
4. **테스트 품질**: 공개 동작을 검증하는가, 내부 구현에 묶였는가. 중요한 동작인데 테스트가 없는 것은.
5. **용어**: 도메인 이름이 `CONTEXT.md`와 맞는가. 용어집에 없는 개념이 생겼거나 _Avoid_ 단어를 쓰는가.
6. **범위**: 다른 이슈의 기능을 미리 만들었는가(과잉). 그것들이 들어올 자리를 막는가.
7. **위생**: 큰 바이너리, `.venv`, 검증 기록 파일이 커밋되지 않았는가. 커밋 메시지가 한국어인가. 비밀 정보나 하드코딩된 절대 경로가 없는가.
8. **버그**: 위와 별개로 실제 동작을 깨뜨리는 결함. 실제 어댑터(ffmpeg 등)로 재현해 볼 수 있으면 재현한다. 테스트 영상은 `<메인 저장소>/.local/테스트 라이브러리/`에 있다.

## 제약

검토 전용. 파일을 수정하거나 커밋하지 않는다. 임시 스크립트는 worktree 밖에서 돌리고 흔적을 남기지 않는다. 추측성 지적은 하지 않고, 지적마다 재현 방법이나 근거(파일과 줄, 실행 결과)를 붙인다. 화면을 직접 띄워 보는 확인은 사람 몫이다.

## 결과

상세 결과를 `<보고서 절대 경로>`에 쓰고 `--report-path`로 넘긴다. `worker_done` 요약은 3문장 이내로 결론만.

- 결론: 통과 / 수정 필요
- 완료 기준 판정표 (항목 / 판정 / 근거)
- pytest 실행 결과
- 지적 목록: 심각도(차단 / 중요 / 사소) · 내용 · 근거 · 제안
- 사람이 직접 확인해야 할 항목
```

## 재검토

재검토는 **차단·중요 지적을 고쳤을 때만** 한다(SKILL.md 5단계). 사소한 지적만 고쳤으면 관리자가 직접 확인한다.

재검토는 같은 검토자 터미널에 짧은 명세로 맡긴다.
- 대상: `git diff <이전 커밋>..HEAD`와 브랜치 전체
- 판정 대상: "지금 고침"으로 정한 지적 목록. 넘긴 지적은 판정하지 않는다.
- 앞선 재현 절차를 다시 돌려 확인하고, 새 결함이 있는지 본다.
- 테스트는 수정분과 관련된 것만 돌린다. 전체 pytest는 돌리지 않는다.

보고서는 `rereview-<k>.md`로 따로 쓴다.
